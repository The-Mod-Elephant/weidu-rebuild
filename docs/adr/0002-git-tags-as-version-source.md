# ADR 0002: Git tags are the only version source

- Status: Accepted
- Date: 2026-10-25, revised for the release flow of #20

## Context

Versions must follow SemVer 2.0.0, and a release must report the version it was published as.
A second, independently edited version source can drift from the tags.

## Decision

- Release tags `vX.Y.Z` are the single source of truth for the application version. A
  maintainer chooses the next version by hand, following SemVer 2.0.0, and pushes the tag to a
  commit on `main`.
- Pushing the tag runs `.github/workflows/build.yaml` for that tag. Its builds receive the version
  at compile time through `IEMOD_RELEASE_VERSION` (the tag without its leading `v`), and every
  other build reports `0.0.0-dev`. Its `trigger-release` job then starts
  `.github/workflows/release.yaml` on the same tag with the build's run ID, and that workflow
  publishes the build's artifacts as the GitHub Release for the tag.
- There is no `VERSION` file and no committed `CHANGELOG.md`; the release notes are generated by
  GitHub (`gh release create --generate-notes`).
- The `version` field in `Cargo.toml` is not authoritative and is not kept in sync with the tags.
  It exists because `default.nix` passes it to `buildRustPackage`.

## Consequences

- No bot needs write access to `main`, and no secret beyond the workflow token is required.
- Choosing the version is a manual step. Nothing checks it against the Conventional Commits since
  the previous tag, so the maintainer applies the SemVer rules ([READINESS.md](../release/READINESS.md)).
- Tools that read `Cargo.toml`, including the Nix package, see its placeholder `version`; the
  authoritative version is the tag, or `iemod --version` of a release build.
